# 勤怠ハブ MVP 仕様(v2 — レビュー反映版)

PoC 3本(レバテック勤怠入力・Typeform 申請・Google カレンダー登録)がすべて Go 判定となったため、MVP のスコープと設計を定義する。検証済みの技術詳細は [POC_STORY.md](../history/POC_STORY.md) 参照。

v1 に対する2系統のレビュー(プロダクト観点・技術/安全観点)の指摘を反映済み。v1 の弱点は「検証済みの操作には厚く、データのライフサイクルと状態管理には薄い」だった。

## 1. コンセプト

> 例外日(休暇・遅刻早退)と基本勤務時間を一箇所で管理し、月末にボタン一つでレバテックに自動入力する。例外日の発生時は申請とカレンダー登録も一度の操作で済ませる。

- 対象ユーザー: 本人のみ(シングルユーザー・ローカル実行)
- 動作環境: ローカル Mac(Playwright + 実 Chrome。Typeform アダプタの制約)

## 2. 全体構成

```
┌─ ローカル Web アプリ(127.0.0.1 のみ bind)─────────┐
│  UI(ブラウザ)                                     │
│   ├─ フロー①: 月末勤怠入力                          │
│   └─ フロー②: 例外日の申請・登録                     │
│  Node サーバー                                      │
│   ├─ 例外日ストア(JSON・原子的書き込み)              │
│   ├─ ジョブキュー(ブラウザ自動化は直列・同時1件)      │
│   ├─ レバテックアダプタ(Playwright・PoC 03 流用)     │
│   ├─ Typeform アダプタ(Playwright・PoC 04 流用)     │
│   └─ カレンダーアダプタ(HTTP POST・PoC 05 流用)      │
└────────────────────────────────────────────┘
```

GAS Web App はデプロイ済みの本番資産としてそのまま使う。

## 3. データ設計(ハブの核)

### 3-1. 例外日レコード

```
{
  id:        UUID(一意識別子。カレンダーのタグにもこの id を使う)
  date:      'YYYY-MM-DD'(ストアの日付は全て ISO 8601。各アダプタが送信時に変換)
  endDate:   'YYYY-MM-DD' | null(連続休暇)
  kind:      vacation | late | early | custom
  time:      'HH:MM'(late=出社時刻 / early=退社時刻)
  start/end/rest: custom のみ(任意の勤務時間指定)
  reason:    理由(Typeform 送信用)
  statuses:  下記 3-3
  snapshot:  Typeform に実際に送信した内容の写し(送信後に保存)
  cancelled: boolean(論理削除。物理削除はしない)
  createdAt / updatedAt
}
```

- **申請要否は kind で決まる**: `vacation / late / early` は要申請(フロー②で作成)。`custom`(申請不要の時間変更)のみフロー①から追加でき、申請フローを起動しない。**客先休業日も `vacation` として扱う**(客先休業でも休暇申請が必要な運用のため、自分で取る休暇と区別しない)。これにより「未申請バッジ=異常」が常に成立し、警告として機能する
- 同一日に矛盾するレコード(休暇と遅参など)はストア層でバリデーションエラー
- 祝日はレコードではなく同梱の祝日データ(holiday-jp 系 npm パッケージ)で自動判定

### 3-2. 編集・取り消しの意味論

- **編集可能なのは未申請レコードのみ**。申請済み(submitted 以降)は日付・種別・時刻を編集不可
- 申請済みの内容を変えたい場合は「**取り消し → 新規作成**」フロー: Typeform の種別「前回ご連絡の取り消し」で取り消し申請を送り、レコードを `cancelled` にし、UI が「カレンダーの予定を手動削除してください」とチェックリスト表示(差分同期はスコープ外のため)。その後、新しい内容で新規レコードを作る
- `cancelled` レコードはフロー①のスキップ判定から除外される(取消済みの休暇日に勤怠が入らない事故を防ぐ)

### 3-3. 反映ステータス(ブールではなくステートマシン)

| 反映先 | 状態遷移 |
|---|---|
| Typeform | `none → submitting → submitted / failed / unknown` |
| カレンダー | `none → registered / failed`(冪等のため再実行自由) |
| レバテック | フロー①の実行記録として反映月を保持 |

**Typeform の write-ahead 原則**: 送信クリックの**前**に `submitting` を永続化し、完了画面(サンクスページ)の DOM を検出して初めて `submitted` にする。検出できずに終了したら `unknown`。

- `failed` からの再実行: 通常導線で可
- `unknown` からの再実行: **原則ブロック**。「メール通知等で申請の到達を目視確認した」旨のチェックを伴う別導線でのみ、`submitted` への手動確定 or 再送信を許可(取り下げ不可の操作に「警告付き許可」は無意味 — 警告は習慣化して無視されるため)

### 3-4. ストアの永続化

- JSON ファイル。tmp 書き込み → rename の原子的書き込み+世代バックアップ
- Git 管理外。設定ファイル(GAS シークレット等を含む)も同様に Git 管理外と明記

## 4. 機能要件

### F1. フロー①: 月末勤怠入力(レバテック)

**UI**:
- 対象月の選択。デフォルトは「月初5日までは前月、それ以降は当月」(月初に前月分を入れる実運用に合わせる)
- 基本勤務時間の表示・変更(デフォルト 9:00-18:00・休憩 1.0h)
- 例外日一覧(ストア+祝日データから初期表示。`custom` のみこの画面から追加可。休暇・遅参・早帰りの追加は要申請のためフロー②へ誘導)

**[登録] ボタン押下時のジョブ**:
1. セッションのプリフライトチェック(切れていたら中断し、§6 のログイン導線へ)
2. 対象月の作業報告 URL を解決(§7-1 の事前スパイク結果に基づく)。**解決に失敗した場合に備え、URL(id)手動入力欄を必ず用意する**(フォールバック)
3. **月照合ガード**: 開いたページから対象月を読み取り、UI で選択した月と一致しなければ即中断(別の月への誤入力を構造的に防ぐ)
4. 各行の入力値を「期待値照合」方式で決定(§5 の変換表で期待値を計算):
   - 一致 → スキップ / 空欄 → 入力 / **不一致 → 差分としてマークし、この時点では触らない**
5. 不一致があった場合はプレビューに赤字表示し、ユーザーが「上書きを承認」した場合のみ期待値で上書き(承認しなければその行は現状維持)。これにより「月中に入力→後から休暇登録→月末再実行で休暇日に勤怠が残る」事故(v1 の最重要欠陥)を防ぐ
6. 保存クリック前に**全行を再スクレイプして計画と突合**。不一致があれば保存せず中断
7. 「保存する」をクリックし、**「更新しました。」の表示をアサート**して初めて成功とする(検出できなければ failed)
8. 月次の「報告する」は自動化しない(従来どおりの安全設計)

### F2. フロー②: 例外日の申請・登録

**UI**: 種別(お休み・遅参・早帰り)/ 日付(連続休暇は期間)/ 時刻 / 理由

**[登録] ボタン押下時**:
1. **確認ダイアログ**: Typeform へ送信される内容を表示し、明示的な確認後にのみ進む
2. **逐次実行**(並行にしない — 失敗状態の組み合わせを増やさない): まずカレンダー登録(可逆・冪等)、次に Typeform 送信(§3-3 の write-ahead で)
3. レコードと各ステータスを保存。片方失敗はバッジで可視化し、失敗した側だけ再実行可(Typeform は §3-3 のルールに従う)

### F3. 結果表示(v1 の F4 を縮小)

- 例外日一覧の反映ステータスバッジ
- 直近実行の結果サマリ(入力日数・合計時間・エラーメッセージ)
- 失敗時はスクリーンショットのファイルパスを表示(ログビューアは作らない)
- スクリーンショットは jobId ごとのディレクトリに保存(上書きしない)。送信内容の監査ログ(いつ・何を送ったか)を append-only で残す

## 5. 例外日 → レバテック入力値の変換表

基本勤務: 9:00-18:00 / 休憩 1:00(UI で変更した場合はその値を基準に計算)

| kind | 開始 | 終了 | 休憩 |
|---|---|---|---|
| vacation / 祝日 / 土日 | 空欄(入力しない) | 空欄 | 空欄 |
| late(time=出社時刻) | time | 18:00 | 1:00 |
| early(time=退社時刻) | 9:00 | time | time ≤ 13:00 なら 0:00、それ以外 1:00 |
| custom | 指定値 | 指定値 | 指定値 |

※ 休憩ルール(early の 13:00 境界)は暫定。実運用の慣行と異なる場合はここを直す。

## 6. ジョブ実行モデルとセッション管理

- ブラウザ自動化(レバテック・Typeform)は**グローバル直列キュー・同時1ジョブ**(persistent context のプロファイルロック衝突を構造的に回避)。実行中の新規投入は 409 を返し UI はボタンを無効化
- 登録系 API は即座に jobId を返し、UI はポーリング(`GET /api/jobs/:id`)で進捗・結果を取得。UI を閉じてもジョブは完走する
- カレンダーアダプタ(HTTP のみ)はキュー外で実行可
- **セッション切れ対応**: 全レバテックジョブの前段でセッションチェックを必須化。切れていた場合、サーバーが Chrome バイナリを直接 spawn(`--user-data-dir=<絶対パス> --use-mock-keychain` 付き。`open -a` は既存 Chrome に引数を無視されるため使わない)→ ユーザーが手動ログイン →「ログイン後 Chrome を完全終了してください」と案内 → プロファイルロックの解放を検知 → セッションチェックを自動再実行、までを導線として実装

## 7. セキュリティ(localhost でも省かない)

1. `127.0.0.1` のみに bind(`0.0.0.0` 禁止)
2. サーバー起動時に乱数トークンを生成して UI に埋め込み、全変更系 API でカスタムヘッダ必須(cross-origin からは preflight が強制されるため CSRF が構造的に成立しない)
3. Origin / Host ヘッダ検証

背景: 確認ダイアログはブラウザ UI であり、サーバーの API を直接叩かれると「取り下げ不可の申請」が無確認で飛ぶ。対策コストは 30 行程度。

## 8. スコープ外(MVP に含めない)

- 月次「報告する」(請求提出)の自動化
- カレンダーの差分同期(取消時は手動削除。UI がチェックリストで案内)
- 半休・中抜け(遅参かつ早帰り)— kind 単一値では表現不能。必要になったら custom で代用し、頻発するなら次版で kind 追加
- 入力済み値の一括上書きモード(不一致は個別承認のみ)
- 複数ユーザー・認証・クラウドデプロイ・スマホ対応

## 9. 技術方針

- Node.js + ESM。UI は最小構成(Express + 素の HTML/JS。ビルドツール・JS フレームワーク不使用)
- 装飾は Tailwind CSS。ビルドレスを保つため Play CDN(`<script src="https://cdn.tailwindcss.com">`)で導入(ローカルツールのため CDN 依存は許容。オフラインで使いたくなったら standalone CLI で静的生成に切り替え)
- PoC コード(03/04/05)をアダプタ化して流用。ただし PoC は「完走して Enter 待ちする対話スクリプト」なので、ライフサイクル(context の起動・破棄・エラー時クリーンアップ)はジョブキュー側で再設計する
- 設定(レバテック URL・Typeform ID・GAS URL/シークレット・基本勤務時間・ポート番号)は設定ファイルに外出し(Git 管理外)

1. ~~URL 自動解決のスパイク~~ → **検証済み(2026-08-07、06-resolve-url-spike.mjs)**。確定した解決方法:
   - 一覧 `https://platform.levtech.jp/p/work-report/` に全月が表示され、各行は `/p/workreport/{id}/` への実 href を持つ(`<a>` タグ。JS ナビゲーションではない)
   - 行内に期間テキスト `YYYY/MM/01~YYYY/MM/DD` とステータス(要対応/確認待ち/完了)がある → 対象月の期間テキストにマッチする行から id を抽出し、入力 URL は `/p/workreport/input/{id}/`
   - 詳細ページ `/p/workreport/{id}/` に「報告月 YYYY年MM月」の表示がある → **月照合ガードの読み取り元**
   - ステータスが「確認待ち/完了」の月は入力対象外として警告する(要対応のみ入力可とする)
   - 注意: 現在は契約が1つの前提。複数契約になると一覧に複数行グループが現れる可能性があるため、その際は契約名での絞り込みが必要(スコープ外として記録)
2. Typeform の送信(--submit)は実績なし。初回の実申請が実地検証を兼ねる(完了画面検出のセレクタもそこで確定)
3. 外部サービスの画面構造変更リスク: 失敗検出(アサート)とスクリーンショットで「静かに壊れない」ことを担保。Typeform の質問文言変更は rules の正規表現不一致 → 「進めない」エラーとして顕在化する設計を維持
