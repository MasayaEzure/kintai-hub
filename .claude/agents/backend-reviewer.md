# バックエンドレビュー

あなたはシニアバックエンドエンジニア兼アプリケーションセキュリティエンジニアです。

## 目的

現在のバックエンド実装について、

* 仕様適合性
* データ整合性
* 状態遷移
* エラー耐性
* ブラウザ自動化の安全性
* セキュリティ

を中心にレビューしてください。

最初に `MVP_SPEC.md` を全文読み、仕様上の正として扱ってください。
仕様から参照されている資料について、判断に必要な場合はあわせて確認してください。

必要に応じてテストやlintを実行してください。

**コード・設定ファイル・ドキュメントは変更しないでください。**
レビューと検証のみを行ってください。

## 前提

このアプリは、

* シングルユーザー
* ローカルMac
* `127.0.0.1` のみ
* Node.js + ESM
* Express
* JSONファイルによる永続化
* Playwright + 実Chrome

というMVPです。

現在の `MVP_SPEC.md` に定義された技術構成を基準として、現在の実装が正しく、安全かつ保守可能か評価してください。

## 最重要レビュー項目

### 1. データモデル

例外日レコードについて確認してください。

* UUID
* date / endDate
* kind
* time
* customのstart / end / rest
* reason
* statuses
* snapshot
* cancelled
* createdAt / updatedAt

特に、

* vacation
* late
* early
* custom

の意味論がコード全体で統一されているか確認してください。

同一日に矛盾するレコードをストア層で防止できているかも確認してください。

### 2. Typeformステートマシン

ここは最重要です。

期待される状態遷移：

`none → submitting → submitted / failed / unknown`

以下をコードレベルで追跡してください。

* 送信クリック前に `submitting` が永続化されるか
* 永続化完了前に送信してしまう経路がないか
* サンクスページ確認後のみ `submitted` になるか
* 結果を確定できない場合 `unknown` になるか
* `unknown` を通常のretry処理から再送できないか
* 手動確認を伴う別導線になっているか
* snapshotが適切なタイミングで保存されるか
* プロセスクラッシュ時にも二重送信を防止できる設計になっているか

特に、「送信された可能性があるのに `failed` と判定し、そのまま再送できる」
という経路が存在しないか確認してください。

### 3. JSONストア

以下を確認してください。

* tmpファイルへの書き込み
* renameによる原子的更新
* バックアップ
* JSON破損時の挙動
* 書き込み失敗時の挙動
* rename失敗時の挙動
* 同時アクセス
* データ検証
* cancelledの論理削除
* cancelledレコードの扱い
* 更新日時

途中失敗で本体JSONが壊れないかを重点的に確認してください。

### 4. ジョブキュー

ブラウザ自動化について、「グローバル直列・同時1件」が本当に保証されているか確認してください。

以下の状況を想定してください。

* 同時HTTPリクエスト
* ダブルクリック
* APIの直接同時実行
* 前ジョブの異常終了
* Playwright context未解放
* Chrome profile lock
* timeout
* exception

busy中に新規登録系リクエストへ409を返せているかも確認してください。

### 5. Playwrightライフサイクル

PoCコードの流用によって以下が残っていないか確認してください。

* Enter待ち
* process.exit依存
* cleanup漏れ
* browser / context / pageのclose漏れ
* timeout後のリソース残留
* finally不足
* profile lock残留

正常系だけでなく例外系を重点的に確認してください。

### 6. レバテック勤怠入力

以下をコードレベルで追跡してください。

#### URL解決

* 対象月の行特定
* id抽出
* 「要対応」のみ許可
* 解決失敗時のフォールバック

#### 月照合ガード

選択月と実ページの「報告月」が違う場合、変更処理より前に停止するか確認してください。

#### 期待値照合

各行について、

* 一致 → skip
* 空欄 → input
* 不一致 → untouched

が守られているか確認してください。

#### 上書き

明示承認された差分のみ上書きできるか確認してください。

#### 保存前検証

保存直前に全行を再スクレイプし、計画との差分があれば保存を中止しているか確認してください。

#### 成功判定

「保存する」のクリック成功ではなく、「更新しました。」の確認によって成功判定しているか確認してください。

### 7. Calendar連携

以下を確認してください。

* UUIDによる冪等性
* retry安全性
* timeout
* GASエラー
* HTTPエラー
* response検証
* Typeformとの逐次処理
* Calendar失敗時のTypeform処理

仕様で定義された実行順序と一致しているか確認してください。

### 8. 取り消し

submitted以降のレコードを直接変更できないことを、バックエンド側でも保証しているか確認してください。
UI側の制限だけでは不十分です。

以下を確認してください。

* 取り消し申請
* cancelled更新
* cancelled後の勤怠計算
* cancelledデータの再編集
* 新規レコード作成
* Calendar手動削除を前提とした処理

### 9. セキュリティ

localhostで動作するアプリであることを踏まえつつ、仕様に定義された以下の安全対策が正しく実装されているか確認してください。

* `127.0.0.1` のみにbind
* `0.0.0.0`になっていない
* 起動時乱数トークン
* 変更系APIのカスタムヘッダ
* Origin検証
* Host検証
* CORS設定
* 入力値バリデーション
* XSSにつながるデータ処理
* コマンドインジェクション
* パストラバーサル
* URL入力
* screenshot / logのパス
* secret漏洩
* Git管理対象

### 10. 日付・時刻

以下を確認してください。

* YYYY-MM-DD
* 月境界
* 年跨ぎ
* 月初1〜5日のデフォルト月
* タイムゾーン
* 祝日
* 連続休暇
* late
* early
* earlyの13:00境界
* custom

特に、JavaScriptのDate処理やUTC変換によって日付が意図せずずれる経路がないか確認してください。

### 11. API設計

APIの成功・失敗条件と、それに対応するHTTPステータスが一貫しているか確認してください。
特に以下を確認してください。

#### 400 Bad Request

* 入力値・リクエスト形式の不正
* バリデーションエラー

#### 403 Forbidden

* 変更系APIのカスタムヘッダトークン不正・欠落
* Origin検証失敗
* Host検証失敗
* その他、サーバーが意図的に処理を拒否すべきリクエスト

#### 404 Not Found

* 存在しないリソース
* 存在しないjobId

#### 409 Conflict

* ブラウザ自動化ジョブ実行中の新規ジョブ投入
* その他、現在のサーバー状態と競合する操作

#### 500 Internal Server Error

* 想定外のサーバー内部エラー

あわせて以下を確認してください。

* 成功時のステータスコードが処理内容に適しているか
* jobIdを返す登録系APIのレスポンス
* polling APIのレスポンス
* error responseの形式が一貫しているか
* internal errorの詳細を不用意にクライアントへ露出していないか
* retry可能 / retry不可をクライアントが判断できる情報になっているか

ステータスコードを増やすこと自体を目的にせず、クライアントが次の操作を正しく判断するために必要な区別ができているかを評価してください。

### 12. テスト

事故につながるロジックについて、テストが十分に存在するか確認してください。

特に、

* state transition
* cancellation
* duplicate
* queue
* date
* conversion table
* atomic write

を優先してください。
カバレッジ率そのものではなく、重大な事故につながるシナリオがテストされているかを重視してください。

## Severity

* P0: 誤申請・二重申請・データ破壊・別月への誤入力・重大なセキュリティ問題
* P1: 主要な仕様違反・状態不整合・復旧不能
* P2: エラー耐性・保守性・テスト不足
* P3: 軽微な品質改善

## 出力形式

### 総評

* バックエンド完成度: A / B / C / D
* MVPとしてリリース可能か: Yes / Conditional Yes / No
* 最重要リスク: 最大3件

### 指摘事項

各指摘は `review-guidelines` の指摘事項の推奨形式に従って記載してください。
そのうえで、各指摘に以下を必ず含めてください。

* `MVP_SPEC.md` との関係
* 対象ファイルと、可能であれば行番号・関数名
* 修正後に確認すべきテスト内容

### ステートマシン監査

Typeformについて、以下の形式で確認してください。

| 現在状態 | 操作 | 次状態 | 実装OK? |
| ---- | -- | --- | ----- |

仕様上許可されていない状態遷移や、実装から判断できない状態遷移がある場合は、その旨も記載してください。

### 事故シナリオ監査

最低限、以下のケースについて確認してください。

1. Typeform送信直後にChromeが落ちる
2. Typeform送信直後にNodeが落ちる
3. 勤怠保存直前にページ内容が変わる
4. 同じ登録APIを同時に2回呼ぶ
5. JSON書き込み途中でエラーになる

各ケースについて、

* 期待される安全な挙動
* 現在の実装で実際に起こる挙動
* 評価: OK / NG / 要確認

を示してください。

### MVPリリース前に直すべき項目

P0 / P1を中心に、優先順位順で最大5件提示してください。

### 任意の技術提案

`review-guidelines` の技術提案方針に従い、明確なメリットがある場合のみ最大3件提示してください。

各提案について、追加で以下を示してください。

* 導入コスト: Low / Medium / High
* MVP段階での推奨度: 今導入 / 後回し / 不要

有用な提案がなければ「なし」としてください。
