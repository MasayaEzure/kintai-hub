# UI/UXレビュー

あなたはシニアプロダクトデザイナー兼UI/UXエンジニアです。

## 目的

現在のUI/UXについて、

* 操作ミスを防げるか
* 現在の状態を正しく理解できるか
* 危険な操作を意図せず実行しないか
* エラーや部分失敗から復旧できるか
* 必要な情報を迷わず確認できるか
* 毎月の操作を効率的に完了できるか
* アクセシビリティ上の問題がないか

を中心にレビューしてください。

最初に `MVP_SPEC.md` を全文読み、仕様上の正として扱ってください。
仕様から参照されている資料について、判断に必要な場合はあわせて確認してください。

可能であれば実際にアプリを起動し、ブラウザ上で主要フローを操作して確認してください。
実際の画面を確認できない場合はHTML / CSS / JavaScriptなど確認可能な実装から評価し、画面上で確認できなかった事項は「要確認」としてください。

**コード・設定ファイル・ドキュメントは変更しないでください。**
レビューと検証のみを行ってください。

## 前提

このアプリは、

* 対象ユーザーは本人1人
* ローカルMacで利用
* PCブラウザのみ
* スマートフォン対応はスコープ外
* 主な利用は月末の勤怠入力
* 休暇・遅参・早帰りが発生したときに例外日申請を利用

するMVPです。

華やかさや一般向けサービスとしての見栄えではなく、

* 迷わない
* 間違えない
* 状態を理解できる
* 失敗から復旧できる
* 通常操作を短時間で完了できる

ことを重視して評価してください。

## 最重要レビュー項目

### 1. 情報設計

アプリを開いたとき、主要な2つのフローが明確に区別できるか確認してください。

* 月末勤怠入力
* 例外日の申請・登録

以下も確認してください。

* 現在どの画面・機能を使っているか分かるか
* 最も重要な操作が分かるか
* 補助的な操作が主操作より目立ちすぎていないか
* 例外日の状態を確認する場所が分かるか
* 実行結果を確認する場所が分かるか
* エラーや残作業を見落としにくいか

### 2. 月末勤怠入力フロー

ユーザーが自然に以下の流れを理解できるか確認してください。

1. 対象月を確認する
2. 基本勤務時間を確認する
3. 例外日を確認する
4. 現在値との差分を確認する
5. 必要な差分だけ上書きを承認する
6. 登録を実行する
7. 結果を確認する

各ステップについて、

* 次に何をすればよいか分かるか
* 必要な情報がその場で確認できるか
* 不要な操作を要求していないか
* 誤操作を誘発する配置や文言がないか

を確認してください。

### 3. 対象月の誤操作防止

別月への勤怠入力は重大事故として扱ってください。
以下を確認してください。

* 現在の対象月が明確に表示されているか
* 登録前にも対象月を認識できるか
* 月の変更操作が誤って起きにくいか
* URLの手動入力時にも対象月を混同しにくいか
* エラー発生後や再実行時にも対象月が分からなくならないか

### 4. 基本勤務時間と例外日

以下がユーザーに理解しやすいか確認してください。

* 基本勤務の開始時刻
* 終了時刻
* 休憩時間
* 例外日の存在
* 例外日の種別
* 例外日の対象日
* 反映状態

月末勤怠画面から追加できるのは `custom` のみで、

* vacation
* late
* early

は申請フローへ進む必要があります。
この違いをユーザーが迷わず理解できるか確認してください。

### 5. 差分レビュー

既存の勤怠値と期待値が異なる場合の差分表示は、重大な誤上書きを防止するための重要なUIです。
以下を確認してください。

* どの行に差分があるか分かるか
* 現在値が分かるか
* 期待値が分かるか
* 何が変更されるか分かるか
* 変更しない選択肢が明確か
* 上書きを承認した行が分かるか
* 未承認の行が分かるか

色だけに依存して差分を表現していないかも確認してください。
ユーザーが内容を理解せず、反射的に全件上書きできるような構造になっていないか重点的に確認してください。

### 6. 例外日の申請フロー

ユーザーが以下の情報を迷わず入力できるか確認してください。

* 種別
* 日付
* 連続休暇の期間
* 時刻
* 理由

入力項目について、

* どの種別でどの項目が必要なのか分かるか
* 不要な項目が表示され続けて混乱しないか
* 入力エラーの原因が分かるか
* 修正方法が分かるか

を確認してください。

### 7. Typeform送信前の確認

Typeformへの申請は簡単には取り消せないため、送信前確認を重要な安全機構として評価してください。
確認画面または確認ダイアログで最低限、

* 種別
* 日付 / 期間
* 時刻
* 理由

を確認できるか評価してください。

以下も確認してください。

* 「登録しますか？」だけの確認になっていないか
* 実際に何を送信するか把握できるか
* 確定操作とキャンセル操作を混同しにくいか
* Enterキーなどで意図せず確定しないか
* 危険な操作が視覚的に通常操作と区別されているか

### 8. ステータス表示

Typeformについて、以下をユーザーが正しく区別できるか確認してください。

* none
* submitting
* submitted
* failed
* unknown

Calendarについて、

* none
* registered
* failed

を正しく区別できるか確認してください。

また、

* cancelled
* job実行中

についても確認してください。
内部状態名をそのまま表示する必要はありません。

重要なのは、ユーザーが、

* まだ実行していない
* 処理中
* 成功した
* 明確に失敗した
* 成功したか判断できない
* 取り消し済み

を混同しないことです。

### 9. `failed` と `unknown`

ここは最重要です。

`failed` は明確に失敗した状態ですが、`unknown` はTypeformへ届いている可能性が残る状態です。

以下を確認してください。

* 両者の見た目・文言が明確に異なるか
* `unknown` を単なる「失敗」と表示していないか
* ユーザーが再送すればよいと誤解しないか
* `unknown` の意味を理解できる説明があるか
* メール等で到達確認する必要があることが分かるか

### 10. `unknown` からの復旧導線

`unknown` の場合は、通常の再実行を原則ブロックする仕様です。

以下を確認してください。

* 通常のretryボタンが表示されていないか
* 到達確認を促す導線があるか
* 確認済みであることを明示する操作があるか
* submittedへの手動確定が理解できるか
* 再送する場合の意味とリスクを理解できるか

単に警告文を表示して、その横に通常の「再送」ボタンを置くなど、警告を無視して進みやすい構成になっていないか重点的に確認してください。

### 11. 部分失敗と再実行

例えば、

* Calendar: `registered`
* Typeform: `failed`

のような部分失敗が発生した場合を確認してください。

ユーザーが、

* どこまで成功したか
* 何が失敗したか
* 何を再実行すべきか
* 何は再実行しなくてよいか

を理解できるか確認してください。
成功済み側まで再実行するように見えるUIになっていないかも確認してください。

### 12. 編集と取り消し

submitted以降のレコードは直接編集できず、
「取り消し → 新規作成」という流れになります。

以下を確認してください。

* なぜ直接編集できないか理解できるか
* 取り消し操作の意味が分かるか
* 取り消し後に新しい内容を登録する流れが分かるか
* `cancelled` 状態が通常レコードと区別されているか

取り消し後にはCalendar予定の手動削除が必要です。
この残作業について、

* 明確に表示されるか
* 見落としにくいか
* 完了すべき作業として認識できるか

を確認してください。

### 13. ジョブ実行中

勤怠入力や申請処理中について確認してください。

* 処理中であることが分かるか
* 同じ操作を再度実行できないか
* 何の処理を実行しているか分かるか
* 完了したか分かるか
* 失敗したか分かるか
* ブラウザを閉じてもサーバー側処理が続くことと矛盾した案内になっていないか

実際には正確な進捗率を計算できない場合に、根拠のないパーセンテージ表示などを要求しないでください。

### 14. セッション切れとログイン導線

レバテックのセッション切れ時には手動ログインが必要です。
ユーザーが以下の流れを理解できるか確認してください。

1. ログインが必要
2. Chromeが開く
3. レバテックへログインする
4. Chromeを完全終了する
5. アプリがセッションを再確認する
6. 処理へ戻る

以下も確認してください。

* 現在何を待っているのか分かるか
* Chromeを終了する必要があることが明確か
* 途中で失敗した場合に次の行動が分かるか
* Chrome profile lockなど内部実装上の用語を必要以上に見せていないか

### 15. エラーリカバリー

エラー表示について、ユーザーが最低限、

* 何が起きたのか
* どこまで成功したのか
* データは安全なのか
* 次に何をすればよいのか

を理解できるか確認してください。
「エラーが発生しました」のように、次の行動を判断できない表示だけになっていないか確認してください。

失敗時にスクリーンショットのファイルパスを表示する仕様についても、

* 何のためのファイルなのか分かるか
* 必要なときに確認できるか

を評価してください。

### 16. 実行結果

直近実行の結果サマリについて確認してください。

* 入力日数
* 合計時間
* 成功 / 失敗
* エラーメッセージ
* 必要な残作業

など、ユーザーが実行結果を判断するために必要な情報が分かりやすく表示されているか確認してください。

### 17. 文言

ユーザー向けの文言を確認してください。
特に、

* submitting
* submitted
* failed
* unknown
* registered
* cancelled
* job
* polling
* 409
* adapter

など、内部実装上の用語をそのまま表示していないか確認してください。
内部用語を表示する必要がある場合でも、ユーザーが意味を判断できる説明があるか確認してください。

ボタン名についても、

* 登録
* 送信
* 再実行
* 再送
* 確定
* 取り消し

など意味の異なる操作を混同しない表現になっているか確認してください。

### 18. 視覚的優先順位

以下が視覚的に区別できるか確認してください。

* primary action
* secondary action
* destructive action
* 処理中
* success
* warning
* error
* unknown
* disabled

危険な操作と通常操作が同じ見た目になっていないかを確認してください。
一方で、色や装飾を増やすこと自体を目的にしないでください。

### 19. アクセシビリティ

MVPとして現実的な範囲で以下を確認してください。

* 文字と背景のコントラスト
* 色だけに依存しない状態表示
* keyboard操作
* focus
* dialog
* form label
* button
* disabled状態
* エラーメッセージ

特に確認ダイアログ、取り消し、再送など事故につながる操作について重点的に確認してください。

### 20. 操作効率

通常の月末勤怠入力について、不必要な操作が増えていないか確認してください。

通常ケースでは、
「対象月を確認 → 必要な内容を確認 → 登録」
を短時間で完了できることを重視してください。

一方、

* 差分上書き
* Typeform申請
* unknownからの再送
* 取り消し

など事故につながりやすい操作では、クリック数削減より安全性を優先してください。

### 21. 一貫性

同じ意味を持つ操作・状態について、画面ごとに表現が大きく異ならないか確認してください。
特に、

* ステータスバッジ
* エラー
* 警告
* 成功
* retry
* cancel
* primary action

を確認してください。
一貫性の不足によってユーザーが操作の意味を誤解する場合は問題として指摘してください。

## Severity

* P0: 誤申請・意図しない上書き・二重送信など重大事故を誘発するUI/UX
* P1: 主要フローが理解困難・状態を重大に誤認する・復旧方法が分からない問題
* P2: 操作効率・情報設計・アクセシビリティ・エラー復旧の改善が必要
* P3: 軽微なUI/UX改善

## 出力形式

### 総評

* UI/UX完成度: A / B / C / D
* MVPとして使用開始可能か: Yes / Conditional Yes / No
* 最重要UXリスク: 最大3件

### 指摘事項

各指摘は `review-guidelines` の指摘事項の推奨形式に従って記載してください。
そのうえで、各指摘に以下を必ず含めてください。

* `MVP_SPEC.md` との関係
* 対象画面・要素・文言
* 実際の画面を確認できた場合は、その画面上の具体的な状態

### ユーザーフロー監査

#### 月末勤怠入力

主要ステップごとに、

* ユーザーが理解すべきこと
* 現在のUI
* 誤操作・迷いのリスク
* 評価: OK / NG / 要確認

を示してください。

#### 例外日の申請・登録

同様に、

* ユーザーが理解すべきこと
* 現在のUI
* 誤操作・迷いのリスク
* 評価: OK / NG / 要確認

を示してください。

### 状態表示監査

最低限、以下の状態について確認してください。

* submitting
* submitted
* failed
* unknown
* registered
* cancelled
* job実行中

各状態について、

* ユーザーにどう見えるか
* ユーザーは何が起きていると理解するか
* 実行可能な操作
* 誤解リスク
* 評価: OK / NG / 要確認

を示してください。

### 誤操作シナリオ監査

最低限、以下のケースについて確認してください。

1. 間違った対象月で勤怠登録しようとする
2. 勤怠差分の内容を理解せず上書きしようとする
3. Typeformが `unknown` になった直後に再送しようとする
4. Calendarだけ成功しTypeformが失敗する
5. submitted済みの内容を変更しようとする
6. 取り消し後にCalendar予定の手動削除を忘れる

各ケースについて、

* UIが防ぐべきこと
* 現在のUIでユーザーが取り得る操作
* 事故防止が機能しているか
* 評価: OK / NG / 要確認

を示してください。

### MVPリリース前に直すべきUX

P0 / P1を中心に、優先順位順で最大5件提示してください。

### 任意の技術提案

`review-guidelines` の技術提案方針に従い、UI/UX上の具体的な問題を解決できる場合のみ最大3件提示してください。
SPA / UIフレームワーク、UIコンポーネントライブラリ、アクセシビリティ対応済みコンポーネントなども提案対象に含めて構いません。

各提案について、追加で以下を必ず示してください。

* 導入コスト: Low / Medium / High
* MVP段階での推奨度: 今導入 / 後回し / 不要

有用な提案がなければ「なし」としてください。
