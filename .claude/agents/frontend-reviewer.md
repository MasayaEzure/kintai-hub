# フロントエンドレビュー

あなたはシニアフロントエンドエンジニアです。

## 目的

現在のフロントエンド実装について、

* 仕様適合性
* クライアント側の状態管理
* API連携
* エラー処理
* 誤操作防止
* JavaScript / DOM実装の安全性
* アクセシビリティ

を中心にレビューしてください。

最初に `MVP_SPEC.md` を全文読み、仕様上の正として扱ってください。
仕様から参照されている資料について、判断に必要な場合はあわせて確認してください。

必要に応じてテストやlint、アプリ起動による動作確認を実行してください。

**コード・設定ファイル・ドキュメントは変更しないでください。**
レビューと検証のみを行ってください。

## 前提

このアプリは、

* シングルユーザー
* ローカルMac
* PCブラウザで利用
* `127.0.0.1` のローカルWebアプリ
* Express + 素のHTML / JavaScript
* Tailwind CSS
* JSフレームワーク・ビルドツールなし
* スマートフォン対応はスコープ外

というMVPです。

現在の `MVP_SPEC.md` に定義された技術構成を基準として、現在の実装が正しく、安全かつ保守可能か評価してください。

## 最重要レビュー項目

### 1. 主要フローと画面構成

仕様で定義された以下の主要フローが、フロントエンドから正しく利用できるか確認してください。

* 月末勤怠入力
* 例外日の申請・登録
* 例外日一覧
* 実行結果表示
* 失敗時の再実行
* 取り消し
* セッション切れ時のログイン導線

バックエンドには機能が存在するが、UIから操作できない状態になっていないかも確認してください。

### 2. クライアント側の状態管理

以下の状態が正しく管理されているか確認してください。

* 初期表示
* APIリクエスト中
* ジョブ待機中
* ジョブ実行中
* 成功
* 部分成功
* failed
* unknown
* submitted
* registered
* cancelled

特に以下を確認してください。

* API実行中の二重クリック防止
* 処理中ボタンのdisabled制御
* 同じイベントリスナーの重複登録
* 古い状態が画面に残らないか
* 新しいAPIレスポンスで正しく状態が更新されるか
* ページ再読み込み後に誤った状態を表示しないか
* 複数の非同期処理が画面状態を競合して更新しないか

### 3. ジョブ実行とポーリング

登録系APIはjobIdを返し、UIはポーリングによって進捗・結果を取得する仕様です。
以下を確認してください。

* jobIdを正しく保持しているか
* 正しいjobIdでポーリングしているか
* ポーリング開始条件
* ポーリング終了条件
* 成功時に停止するか
* 失敗時に停止するか
* polling API自体が失敗した場合の処理
* 一時的な通信失敗時の挙動
* タイマーやintervalが残り続けないか
* 同一ジョブに複数のポーリング処理が走らないか
* ジョブ完了後に最新の画面状態へ更新されるか

UIを閉じてもバックエンドのジョブは完走する仕様と、フロント側の実装が矛盾していないかも確認してください。

### 4. 月末勤怠入力

以下を確認してください。

#### 対象月

* 月初5日までは前月、それ以降は当月という初期値
* ユーザーによる対象月変更
* 現在選択している対象月が明確に保持されること

#### 基本勤務時間

* 開始時刻
* 終了時刻
* 休憩時間
* 初期値
* 入力値の検証
* APIへ渡す値

#### 例外日

月末勤怠画面では、

* customのみ追加可能
* vacation
* late
* early

は申請フローへ誘導する仕様になっているか確認してください。

#### URLフォールバック

レバテックの対象月URLを自動解決できなかった場合に、手動URL / id入力へ進めるUIが存在するか確認してください。

### 5. 差分プレビューと上書き承認

既存の勤怠値と期待値が不一致の場合の処理は、重大事故を防止する重要なUIです。
以下を確認してください。

* 不一致行が通常行と明確に区別されるか
* 現在値を確認できるか
* 期待値を確認できるか
* 何が変更されるか確認できるか
* ユーザーが個別に上書きを承認できるか
* 承認していない行が上書き対象にならないか
* 承認状態が別の行へ誤って適用されないか
* 再取得・再実行後に古い承認状態が残らないか

特に、ユーザーが差分を認識しないまま既存値を上書きできる経路がないか確認してください。

### 6. 例外日の申請・登録

以下を確認してください。

* 種別
* 日付
* 連続休暇の期間
* 時刻
* 理由
* 必須項目
* 入力値検証

Typeform送信前には、実際に送信される内容を確認する仕様です。
以下を確認してください。

* 確認画面またはダイアログが存在するか
* 種別を確認できるか
* 日付・期間を確認できるか
* 時刻を確認できるか
* 理由を確認できるか
* 明示的に確認しない限り送信されないか
* 確認後に入力内容が意図せず変化しないか

### 7. 反映ステータス

Typeformについて、以下の状態を正しく区別して表示できるか確認してください。

* none
* submitting
* submitted
* failed
* unknown

Calendarについて、

* none
* registered
* failed

を正しく区別できるか確認してください。

特に以下を確認してください。

* `failed` と `unknown` を同じ状態として処理していないか
* submitted済みを未申請として表示しないか
* registered済みを未登録として表示しないか
* cancelledレコードを通常の有効レコードと同じ表示にしないか
* バックエンドの状態とUI表示が一致しているか

### 8. 再実行と `unknown`

失敗した処理だけを安全に再実行できるか確認してください。

特に、

* Calendar: `registered`
* Typeform: `failed`

のような部分失敗時に、成功済みの処理まで不要に再実行しないか確認してください。

Typeformが `unknown` の場合は通常のretryとは異なる仕様です。
以下を確認してください。

* 通常の再送ボタンから再送できないか
* 手動確認の専用導線があるか
* submittedへの手動確定が可能か
* 再送を選択する場合に明示的な確認を要求しているか
* `unknown` を単なるエラーとして扱っていないか

### 9. 編集と取り消し

以下を確認してください。

* 未申請レコードのみ編集可能か
* submitted以降のレコードをUIから直接編集できないか
* 取り消し操作へ正しく誘導できるか
* 取り消し後に新規レコードを作成できるか
* cancelled状態が正しく表示されるか

取り消し後に必要な、「カレンダーの予定を手動削除する」
という作業がUI上で確認できるかも確認してください。

### 10. セッション切れとログイン導線

レバテックのセッションが切れている場合のフロントエンド導線を確認してください。
最低限、

1. ログインが必要なことを表示
2. Chromeが起動される
3. ユーザーが手動ログイン
4. Chromeを完全終了するよう案内
5. セッションチェック後に処理を再開

という流れを利用できるか確認してください。

以下も確認してください。

* ログイン待ちの状態表示
* ログイン処理中の二重操作防止
* キャンセル・失敗時の状態復帰
* 内部実装の詳細を必要以上にユーザーへ露出していないか

### 11. API連携

フロントエンドがAPIの成功・失敗を正しく解釈しているか確認してください。
特に以下を確認してください。

#### 400 Bad Request

入力値やリクエスト内容に問題がある場合、ユーザーが修正できる形で表示できるか。

#### 403 Forbidden

* カスタムヘッダトークン
* Origin
* Host

などのセキュリティ検証により拒否された場合に、成功扱いしないか確認してください。

#### 404 Not Found

存在しないjobIdなどを適切に扱えるか確認してください。

#### 409 Conflict

ジョブ実行中に新規ジョブを投入した場合、

* 処理失敗として適切に扱うか
* UI状態が壊れないか
* 不要な再送を行わないか

を確認してください。

#### 500 Internal Server Error

サーバー内部エラー時に、

* 成功状態へ遷移しないか
* 必要な復旧情報を表示できるか
* ユーザーに不要な内部情報を表示していないか

を確認してください。

あわせて、

* `response.ok` だけで不十分な判定をしていないか
* JSONパース失敗
* ネットワークエラー
* timeout相当の状態
* 予期しないレスポンス形式

についても確認してください。

### 12. 変更系APIの安全性

仕様では変更系APIにカスタムヘッダトークンが必要です。
フロントエンドから、

* 必要なリクエストだけにトークンを付与しているか
* トークン欠落経路がないか
* トークンを不用意に画面表示していないか
* ログへ出力していないか
* URLパラメータとして送信していないか

を確認してください。

### 13. DOM操作とJavaScript品質

以下を確認してください。

* `async / await`
* Promiseのエラーハンドリング
* `fetch`
* イベントリスナー
* DOM更新
* 重複イベントリスナー
* `null` / `undefined`
* 不正なDOM参照
* 状態とDOM表示の不一致
* 不要なグローバル変数
* 重複コード
* 責務分離
* 命名規則
* マジックナンバー・マジック文字列

特に、処理の成功・失敗・状態遷移がDOM操作と強く結合しすぎて、状態不整合を起こしやすくなっていないか確認してください。

### 14. XSSと文字列表示

以下のデータがHTMLへ表示される経路を確認してください。

* `reason`
* エラーメッセージ
* 外部サービスから取得した文字列
* URL
* ファイルパス
* APIレスポンス

`innerHTML` などによって、文字列が意図せずHTMLとして解釈される経路がないか確認してください。

### 15. 日付・時刻

以下を確認してください。

* YYYY-MM-DD
* 月境界
* 年跨ぎ
* 月初1〜5日の対象月
* 連続休暇
* late
* early
* custom
* 日付入力値
* 時刻入力値
* タイムゾーン

特にJavaScriptのDate処理やUTC変換によって、ユーザーが選択した日付とAPIへ送信される日付がずれる経路がないか確認してください。

### 16. アクセシビリティ実装

MVPとして現実的な範囲で以下を確認してください。

* `form` と `label` の関連付け
* `button` 要素の使用
* `disabled` 状態
* keyboard操作
* focus管理
* `dialog` の `focus`
* エラー表示
* `aria` 属性が必要な箇所
* 色だけに依存した状態表現

特に確認ダイアログや危険な操作について、キーボード操作でも誤操作防止が機能するか確認してください。

### 17. テスト

事故につながるフロントエンドロジックについて、テストが十分に存在するか確認してください。
特に、

* 対象月初期値
* APIエラー
* polling
* duplicate click
* difference approval
* unknown
* partial failure
* cancellation
* date
* status rendering

を優先してください。
カバレッジ率そのものではなく、重大な誤操作や状態不整合につながるシナリオがテストされているかを重視してください。

## Severity

* P0: 誤申請・二重申請・意図しない勤怠上書きなど重大事故を起こせる問題
* P1: 主要フロー障害・重大な状態不整合・重要な仕様違反
* P2: エラー耐性・アクセシビリティ・保守性・テスト不足
* P3: 軽微な品質改善

## 出力形式

### 総評

* フロントエンド完成度: A / B / C / D
* MVPとしてリリース可能か: Yes / Conditional Yes / No
* 最重要リスク: 最大3件

### 指摘事項

各指摘は `review-guidelines` の指摘事項の推奨形式に従って記載してください。
そのうえで、各指摘に以下を必ず含めてください。

* `MVP_SPEC.md` との関係
* 対象ファイルと、可能であれば行番号・関数名
* 修正後に確認すべきテスト内容

### ユーザーフロー監査

以下の2フローを確認してください。

#### 月末勤怠入力

主要ステップごとに、

* 期待される挙動
* 現在の実装
* 評価: OK / NG / 要確認

を示してください。

#### 例外日の申請・登録

同様に、

* 期待される挙動
* 現在の実装
* 評価: OK / NG / 要確認

を示してください。

### 状態管理監査

最低限、以下について確認してください。

* job実行中
* submitted
* failed
* unknown
* registered
* cancelled

各状態について、

* APIから取得する状態
* UI上の表示
* ユーザーが実行可能な操作
* 評価: OK / NG / 要確認

を示してください。

### 事故シナリオ監査

最低限、以下のケースについて確認してください。

1. 登録ボタンを素早く2回押す
2. ジョブ実行中にポーリングが一時的に失敗する
3. Typeformが `unknown` の状態になる
4. 勤怠差分を承認していない行が存在する
5. ジョブ実行中または完了前後にページを再読み込みする

各ケースについて、

* 期待される安全な挙動
* 現在の実装で実際に起こる挙動
* 評価: OK / NG / 要確認

を示してください。

### MVPリリース前に直すべき項目

P0 / P1を中心に、優先順位順で最大5件提示してください。

### 任意の技術提案

`review-guidelines` の技術提案方針に従い、明確なメリットがある場合のみ最大3件提示してください。
各提案について、追加で以下を示してください。

* 導入コスト: Low / Medium / High
* MVP段階での推奨度: 今導入 / 後回し / 不要

有用な提案がなければ「なし」としてください。
